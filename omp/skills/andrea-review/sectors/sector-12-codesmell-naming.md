# Sector 12 — Code smell, naming & correctness-detail

## Scope

This sector owns the small-but-load-bearing review concerns Andrea applies *after* the structural races, idempotency gates, and wire contracts are settled: does a name lie about what it caps? Does a hot-path query introduced by the PR lack the partial index the re-cut is the cheap moment to add? Does an idempotent timestamp write re-stamp on repeat? Does a byte-cursor parser handle the BOM it will inevitably see? Is `Utc::now()` at the route layer robbing the money/lifecycle path of an injectable clock, while `Instant::now()` as a latency stopwatch is (correctly) left alone? Is a "one-line fix" claim actually ~15 lines across three files?

Its boundary is the *detail lens*: it does **not** own the concurrency/idempotency *correctness* of the stamp-once guard (that's Sector 01/02), the migration V-number/index *ordering* (Sector 07/09), the 4xx/5xx *recoverability contract* of the 403 misclassification (Sector 08), or the test *coverage* of the s3_client fix (Sector 11). It owns the naming, the missing-index-on-hot-path, the BOM edge, the clock-injection *surface* (not the test that would exercise it), and the honesty of fix-size claims. Where a finding spans both the detail lens and a structural lens, the structural sector is named in Cross-sector links and this sector records only the detail angle.

## Paradigms (7 entries)

### P-12-1: Rename a constant whose name lies about what it caps

**Paradigm statement** — When a constant is compared against column X but named after column Y, the name is a bug-shaped comment: the next reader (or refactor) will "fix" the wrong thing. Rename the constant to match the column it actually gates, or, if the rename is too invasive, add a doc-comment that names the column explicitly and flags the mismatch. A silent rename ask dropped in review is itself a smell — record the decision either way.

**Source evidence** — `gateway.md NIT-1`: "`MAX_ATTEMPTS` is compared against `det_failures`; name reads like it caps `attempt`. Rename to `MAX_DET_FAILURES`." Verdict UNADDRESSED — "Mateo's reply has no entry under NITs for this item — silently dropped with no rationale. The misleading name persists." Reinforced by `feedback-divergences.md`: "Attempt cap counts **deterministic failures**, not lease reclaims … `det_failures` column + bb925ba" — the *whole design point* is that the cap keys on `det_failures`, not `attempt`, yet the constant is named after `attempt`.

**<Provider> infra anchor** — `src/batch/worker.rs:41` (`const MAX_ATTEMPTS: i32 = 3;` — the misleading name, unchanged at PR head); `src/batch/worker.rs:93` (`store::select_exhausted_queued(&state.pool, MAX_ATTEMPTS, ...)` — the constant is passed as the `max_attempts` parameter, which is then bound to the `det_failures` cap); `src/batch/store.rs:549` (`WHERE br.det_failures >= $1` — the parameter bound from `MAX_ATTEMPTS` actually gates `det_failures`, not `attempt`). The schema migration `V44__batch_api.sql:143-150` even *documents* the invariant in prose ("the cap keys on `det_failures`, not `attempt`"), making the Rust-side `MAX_ATTEMPTS` name internally inconsistent with the DB-side doc.

**Codebase-intelligence backend** —
> `codegraph explore -p ~/<provider>/gateway "MAX_ATTEMPTS det_failures select_exhausted_queued"` → confirms the call site that threads the constant into the `det_failures` predicate. (Adversarial note: that multi-keyword query is fuzzy and in practice surfaced `preflight.rs` tangentially — a focused query is `codegraph explore -p ~/<provider>/gateway "select_exhausted_queued max_attempts parameter"`.)
> Serena `find_referencing_symbols` on `MAX_ATTEMPTS` (worker.rs:41) to enumerate every call site before a rename — the constant is module-private (`const`, not `pub`), so the blast radius is one file.
> codebase-memory `search_graph name_pattern=".*MAX_ATTEMPTS.*"` to confirm no second declaration shadows it.

**Fix-suggestion policy** —
> SUGGEST ONLY: open a finding on the PR proposing `MAX_ATTEMPTS` → `MAX_DET_FAILURES` (and the param `max_attempts` → `max_det_failures` in `select_exhausted_queued`), citing the V44 migration's own prose as the authority for the new name. Note the rename is module-private (1 file) + the store signature (1 param). Do NOT commit a patch; the PR author owns the rename and the judgment call of whether it's worth the diff noise now.

**Adversarial caveat** — The constant is module-private and the doc-comment at worker.rs:37-40 already explains the cap keying; a reviewer could legitimately argue the comment is sufficient and the rename is cosmetic diff noise on a PR already carrying 26 review items. The paradigm is strongest when the misleading name has *no* redeeming doc-comment and weakest when, as here, the comment partially compensates — but "partially compensates" is still not "renamed", and a future reader who greps `MAX_ATTEMPTS` expecting attempt semantics will still be misled.

### P-12-2: Add a partial index for every hot-path predicate a re-cut introduces

**Paradigm statement** — When a PR re-cuts a table and adds a query that runs every tick (or every request) with a stable predicate, the same re-cut is the cheap moment to add the supporting partial index. Deferring the index to a later migration means the new query seq-scans on the hot path until someone remembers to come back — and "while you're re-cutting" is the one window where the index lands for free (empty/small table, no backfill, no `CONCURRENTLY` drama). If the predicate is genuinely selective, the index is ~3 lines; if it isn't, that's the decision to record, not a silent drop.

**Source evidence** — `gateway.md NIT-2`: "`select_exhausted_queued` runs every tick with no supporting index on `det_failures` … Andrea framed it as 'cheap to add while you're re-cutting' — a minor perf item, not a correctness issue." Verdict UNADDRESSED — "Silently dropped with no rationale."

**<Provider> infra anchor** — `src/batch/store.rs:538-552` (`select_exhausted_queued` queries `WHERE br.status = 'queued' AND br.det_failures >= $1 AND b.status = 'in_progress' AND b.expires_at > $2`, `ORDER BY b.created_at, br.line_no` — runs every worker tick, no `LIMIT`). The migration `V44__batch_api.sql` defines partial indexes for the *other* hot paths — `idx_batch_request_claim` (`(deployment, batch_id, line_no) WHERE status = 'queued'`, line 180-182) and `idx_batch_request_lease` (`(lease_expires_at) WHERE status = 'in_flight'`, line 185-187) — but **no** index on `det_failures`. The exhaustion sweep reuses the `status = 'queued'` selectivity of `idx_batch_request_claim` but then filters `det_failures >= $1` in a heap scan of the queued partition; with `MAX_DET_FAILURES = 3` and most queued rows at 0, the predicate is selective enough that a partial index `(det_failures) WHERE status = 'queued'` (or a composite `(status, det_failures)`) would shrink the scan to the exhausted minority.

**Codebase-intelligence backend** —
> `codegraph explore -p ~/<provider>/gateway "select_exhausted_queued det_failures partial index"` → locates the query and (if the index existed) the migration that created it.
> codebase-memory `query_graph` Cypher: `MATCH (f:Function {name:'select_exhausted_queued'})-[:CALLS|:REFERENCES]->(n) RETURN n` to see the SQL string node and confirm no `CREATE INDEX … det_failures` neighbor.
> Grep the gateway-db migrations directly: `grep -rn "det_failures" ~/<provider>/worktrees/batch-api/feat-batch-api-gateway-db/migrations/` — confirms the column is defined in V44 but never indexed.

**Fix-suggestion policy** —
> SUGGEST ONLY: open a finding proposing a partial index `CREATE INDEX IF NOT EXISTS idx_batch_request_det_failures ON batch_request (det_failures) WHERE status = 'queued' AND det_failures > 0;` (or composite `(det_failures, batch_id, line_no)` to cover the `ORDER BY`), to land in the *same* V44 re-cut while the table is empty. Cite the sibling `idx_batch_request_claim` / `idx_batch_request_lease` as the established partial-index convention in this migration. Note the index is partial on `status = 'queued'` so it stays small as the table grows. Do NOT commit; the PR author + DB owner own the migration diff and the `CONCURRENTLY` judgment (table is empty at first deploy, so non-concurrent is fine — same call V44 already makes for its other indexes).

**Adversarial caveat** — The exhaustion sweep is a *backstop* ("the worker normally terminalizes a capped row inline", per store.rs:530-532), so the hot path is rarely hit in steady state; with small per-org fleets the heap scan over queued rows may be cheaper than an extra index's write amplification on every `bump_transient_failure`. The paradigm is right *in principle* (index your hot-path predicates) but this specific instance is the marginal case where the index could be premature — which is exactly why the decision should be *recorded*, not silently dropped.

### P-12-3: Stamp-once — guard idempotent timestamp writes against re-stamp

**Paradigm statement** — A timestamp column that records "when X happened" must be written with a guard that makes a repeat call a no-op, not a re-stamp. If the row is already in the target state (or the timestamp is already set), the UPDATE should match zero rows. A write that unconditionally `SET ts = $2 WHERE id = $1` will silently move the recorded "when" forward on every repeat call, corrupting any downstream duration/retention math that trusts the first stamp. "Harmless because nothing reads it yet" is not a decision — it's a deferred bug.

**Source evidence** — `gateway.md NIT-3`: "Repeated cancel re-stamps `cancelling_at` on every call … harmless but stamp-once is more correct." Verdict UNADDRESSED — "Silently dropped. Harmless (no reader), as Andrea conceded, but no explicit decision." Contrast the canonical sibling: `gateway.md MINOR-1` shows `finalize_failure` was *fixed* to add `AND attempt = $7` precisely so a double-reclaim "can't stamp `result_attempt` at a wrong generation" — the same stamp-once discipline, applied where it *does* have a reader.

**<Provider> infra anchor** — `src/batch/store.rs:668-671` (`UPDATE batch SET status = 'cancelling', cancelling_at = $2 WHERE id = $1` — no guard against an already-`cancelling` batch re-stamping). The `cancel_batch` function at `store.rs:608-640` checks `AlreadyTerminal` for `completed | failed | expired | cancelled` (line 631) and refuses `validating` (line 638), but a second `POST /v1/batches/{id}/cancel` on a batch already in `cancelling` falls through to line 665-676 and re-stamps `cancelling_at = $2` with the new `now`. Canonical sibling for the guard shape: `src/batch/billing.rs:127` (`finalize_success` ... `AND attempt = $9`) and `billing.rs:263` (`finalize_failure` ... `AND attempt = $7`) — both stamp-once via the attempt guard. Test that pins the current (unguarded) behavior: `store.rs:1917-1920` asserts `cancelling_at = Some(now)` after the first cancel, but no test exercises the *second* cancel.

**Codebase-intelligence backend** —
> `codegraph explore -p ~/<provider>/gateway "cancel_batch cancelling_at re-stamp"` → locates the UPDATE and its caller. (Adversarial note: this exact multi-keyword query is fuzzy and in practice returned `rate_limit.rs` test code tangentially — prefer `codegraph explore -p ~/<provider>/gateway "cancel_batch AlreadyTerminal cancelling_at UPDATE"`.)
> Serena `find_referencing_symbols` on `cancel_batch` (store.rs:608) to enumerate callers — only `cancel_batch_inner` at `routes/batches.rs:519`.
> codebase-memory `trace_path mode=calls` from `cancel_batch_inner` to confirm the route is the sole entry point (no internal re-cancel path that would make the re-stamp load-bearing).

**Fix-suggestion policy** —
> SUGGEST ONLY: open a finding proposing `UPDATE batch SET status = 'cancelling', cancelling_at = $2 WHERE id = $1 AND status <> 'cancelling'` (or, narrower, `AND cancelling_at IS NULL`), so a repeat cancel on an already-`cancelling` batch no-ops the stamp while still returning `CancelOutcome::Cancelling`. Cite the `finalize_failure` `AND attempt = $7` guard as the in-repo stamp-once convention. Flag that the route should still return 200 (idempotent), not 409 — the guard is on the *write*, not the *response*. Do NOT commit; the PR author owns the guard and the judgment of whether the 2-line WHERE clause is worth it given no current reader.

**Adversarial caveat** — Andrea conceded "harmless (no reader)" and the cancel route is idempotent by design (a second cancel returns the same `Cancelling` outcome); a reviewer could legitimately argue the guard adds WHERE-clause complexity for a column with zero downstream consumers, and that `cancelling_at` is purely informational until the reaper uses it (it doesn't — the reaper at store.rs:711-712 keys on `status = 'cancelling'`, not `cancelling_at`). The paradigm is correct in general but this instance is the weakest of the three NITs; the honest framing is "stamp-once is the right habit, this column doesn't exercise it yet, but the habit costs 2 lines."

### P-12-4: Strip the UTF-8 BOM at every byte-cursor parser boundary

**Paradigm statement** — A parser that splits a caller-supplied byte stream into lines must strip a leading UTF-8 BOM (`U+FEFF`, bytes `EF BB BF`) before the first line, or line 1's JSON (or CSV, or header) parse silently fails on any file a Windows tool or a `>` redirect from a BOM-emitting editor produced. Stripping CRLF and skipping blanks is not enough — the BOM is neither CRLF nor blank, and it survives into `line 1`'s `raw` as an invisible prefix. If the parser already handles one edge (CRLF), the marginal cost of handling the BOM is one `strip_prefix` on the whole text before the loop; the cost of *not* handling it is a "works on my Mac, fails in prod" bug that only surfaces on a real BOM'd upload.

**Source evidence** — `gateway.md Rebuttal (f)`: "JSONL byte-cursor rewrite holds (CRLF, no trailing newline, multibyte round-trip) with one gap: a leading UTF-8 BOM fails line 1 … The BOM gap Andrea flagged as 'worth a targeted fix' is not acted on and not mentioned in Mateo's reply." Verdict PARTIALLY-ADDRESSED (BOM sub-point UNADDRESSED).

**<Provider> infra anchor** — `src/batch/jsonl.rs:49-85` (`parse_input`): the byte-cursor scan strips CRLF (`bytes[end - 1] == b'\r'` at line 76) and skips blanks (`raw.trim().is_empty()` at line 82), but the loop starts at `cursor = 0` (line 65) with no BOM strip — a leading `\u{FEFF}` remains in line 1's `raw`, so `serde_json::from_str` on line 1 fails with a position-0 parse error. The function returns `Err(Vec<LineError>)` with a single `line_no: 1, code: "invalid_json"` — a confusing error for a file that looks fine in a text editor. No in-repo canonical sibling exists: grep for `BOM|bom|0xEF|uFEFF|strip_prefix("\u{FEFF}")|strip_bom` across `~/<provider>/gateway/src` returns **no matches** — this would be the first BOM-handling site in the gateway, so the fix is net-new, not a reference to an existing convention.

**Codebase-intelligence backend** —
> `codegraph explore -p ~/<provider>/gateway "parse_input jsonl byte cursor BOM CRLF"` → locates the parser and (if any) a BOM-handling sibling — confirms none exists.
> Semble `semble_search "strip UTF-8 BOM from file content before parsing"` → checks the app repo for a canonical BOM-strip sibling (app-side `stringEncryption` / upload paths may have one worth citing as cross-repo convention; if so, cite it, else flag net-new).
> Serena `get_symbols_overview` on `src/batch/jsonl.rs` to confirm `parse_input` is the single entry point (no second parser that might already handle BOM).

**Fix-suggestion policy** —
> SUGGEST ONLY: open a finding proposing a one-line BOM strip at the top of `parse_input` *before* the `cursor = 0` assignment: `let text = text.strip_prefix('\u{FEFF}').unwrap_or(text);` (operates on `&str`, so a BOM at byte 0 is a single char; `strip_prefix` is O(1)). Add a test: a JSONL input beginning with `EF BB BF` byte-for-byte parses with the BOM removed from line 1. Cite that the CRLF strip (line 76) is the established "handle the byte-level edge at the boundary" convention this fix extends. Do NOT commit; the PR author owns the fix and the choice of `strip_prefix` vs a byte-level `bytes.strip_prefix(&[0xEF, 0xBB, 0xBF])` (the latter is safer if a non-UTF-8 path ever feeds `parse_input`, though `String::from_utf8` at `routes/batches.rs:259` already guarantees UTF-8 before this function is called).

**Adversarial caveat** — The caller (`routes/batches.rs:259-260`) does `String::from_utf8(bytes).map_err(|_| ... "must be UTF-8 JSONL")` *before* `parse_input`, so the input is guaranteed UTF-8 and a BOM would survive as `'\u{FEFF}'`; the fix is correctly a `&str` `strip_prefix`. The strongest counter is "BOM'd batch inputs are vanishingly rare in an API-driven flow" — but the cost is one line and one test, and the failure mode (a confusing `invalid_json` on line 1 of a file that renders correctly in every editor) is exactly the kind of "works on my machine" bug that costs hours to diagnose. Andrea's own framing — "worth a targeted fix" — is the bar.

### P-12-5: Inject the clock into every route that stamps lifecycle or money timestamps

**Paradigm statement** — When the worker/reaper/sweep are wired with an injected `Clock` so lifecycle and money paths can be driven on a `ManualClock` in tests, the injection is incomplete if route handlers that stamp lifecycle timestamps (`expires_at`, `cancelling_at`, `cancelled_at`) call `Utc::now()` directly. The create-to-expire path then can't be tested under a deterministic clock, and the "money path is clock-injected" claim is only half true. The fix is to thread the clock through `AppState` (or a route-level extractor), not to special-case each handler. Deferring is legitimate *if* the deferral records why (e.g. "AppState has no clock field; plumbing costs ~10 lines across 6 files for a trivial `now + 24h`; the money decision path is in the reaper, already injected") — but the deferral must be *recorded*, not silent.

**Source evidence** — `gateway.md MINOR-4`: "create/cancel handlers call `Utc::now()` directly (`batches.rs:234, 279, 514`), so the create-to-expire path can't be driven on a `ManualClock`." Mateo: "Deferred — `AppState` has no clock field; plumbing costs ~10 lines across 6 files for a trivial `now + 24h` calc. The money path (expiry decision) is in the reaper, already clock-injected and tested. Will do it when a field is next added to `AppState` or when a lifecycle integration test becomes a requirement." Verdict DECIDED-NOT-ACTIONED — and, notably, *decided with a recorded rationale*, unlike the three silent NIT drops. Also `feedback-divergences.md`: "Injectable clock for expiry/cancel races ✅ Built; called out in PR summary and conformance matrix" — the clock *was* built, just not threaded to the route layer.

**<Provider> infra anchor** — `src/routes/batches.rs:238` (`let now = Utc::now().trunc_subsecs(6);` in create — feeds `expires_at = now + Duration::hours(24)` at line 283, the 24h completion-window lifecycle boundary); `src/routes/batches.rs:518` (`let now = Utc::now().trunc_subsecs(6);` in cancel — feeds `cancel_batch(... now)` which stamps `cancelling_at`/`cancelled_at`). These are the **only two** lifecycle-stamping `Utc::now()` calls in the batch routes (Mateo's correction that line 280/283 is a downstream use of line 238's `now`, not a third call, is verified: line 283 is `let expires_at = now + Duration::hours(24);`). The injected clock exists: `src/batch/worker.rs:672` (`spawn(state: AppState, clock: Arc<dyn Clock>, stop: ...)`), `src/batch/reaper.rs:77` (`spawn(pool, clock: Arc<dyn Clock>)`), `src/batch/sweep.rs:154` (`spawn(state, clock: Arc<dyn Clock>)`) — the clock is a *separate spawn param*, not an `AppState` field, which is exactly why the route handlers (which receive only `&AppState`) can't reach it. Confirmed: `src/main.rs:48-101` (`AppState` struct) has **no** `clock` field. Canonical sibling for the injectable clock: `src/clock.rs` (`Clock` trait, `ManualClock` impl tested at clock.rs:89-92).

**Codebase-intelligence backend** —
> `codegraph explore -p ~/<provider>/gateway "AppState clock field spawn worker reaper"` → confirms the clock is threaded as a spawn param, not via AppState.
> Serena `find_symbol` on `AppState` (main.rs:48) to list its fields and confirm no `clock`; `find_referencing_symbols` on the `Clock` trait (clock.rs) to enumerate every consumer — the three spawn sites and zero route handlers.
> Grep the route layer for the smell directly: `grep -rn "Utc::now()" src/routes/` — surfaces every lifecycle-stamping call (admin.rs:246 key-expiry, admin.rs:825 key-expiry-compare, usage.rs:348-349/507-508/717-718 lookback-defaults, models.rs:128 timestamp, batches.rs:238/518). Not all of these are smells — see P-12-6's adversarial scoping.

**Fix-suggestion policy** —
> SUGGEST ONLY: open a finding noting that clock injection stops at the route layer for lifecycle-stamping writes (create's `expires_at`, cancel's `cancelling_at`/`cancelled_at`), and that the deferred fix is "add `clock: Arc<dyn Clock>` to `AppState`, thread from `main.rs`'s existing `clock` instance, replace the two `Utc::now()` calls in `batches.rs`". Cite that the injected clock already exists (`clock.rs`) and is already wired to the three background spawns — this is plumbing completion, not new infrastructure. Record Mateo's deferral rationale as the decision (not a silent drop) so the lifecycle-integration-test gap is discoverable. Do NOT commit; the PR author owns the ~10-line plumbing and the timing (next `AppState` field addition or lifecycle-test requirement).

**Adversarial caveat** — The deferral is genuinely defensible: the *money* decision (expiry → `finalize_failure` / sweep) is in the reaper, which IS clock-injected and tested; the route's `expires_at` is a create-time write of `now + 24h` that is never re-evaluated against the clock, so a `ManualClock` at the route would only test the arithmetic, not a race. And the route layer is rife with *other* `Utc::now()` calls that are NOT smells — `usage.rs` lookback defaults (read-only query bounds), `admin.rs:825` key-expiry comparison (read-only), `models.rs:128` model-allow timestamp. The paradigm must be scoped to **writes that stamp lifecycle/money timestamps**, not "any `Utc::now()` in a route" — over-applying it produces a pile of false positives on read-only defaults. The strongest form of the paradigm is: "the clock must reach every *write* that a lifecycle/money test would want to drive", not "purge `Utc::now()` from the route layer".

### P-12-6: Don't flag a latency stopwatch as a missing-clock smell

**Paradigm statement** — `Instant::now()` used as a *latency stopwatch* (start time fed to an elapsed-ms metric or a routing decision that depends only on *duration*, not wall-clock value) is not a clock-injection smell and must not be swept up by the "inject the clock" paradigm. The injectable `Clock` exists for *wall-clock* decisions (expiry, cancel, lease boundaries); `Instant` is monotonic, not wall-clock, and is the correct type for "how long did this take". A reviewer who flags `Instant::now()` as "mixed clock usage" is over-applying the clock-injection lens — and the honest move, when caught, is to retract the flag explicitly rather than leave the author half-fixing a non-issue.

**Source evidence** — `gateway.md` "Where you're right — worker.rs:382 Instant::now() is fine": "`Instant::now()` at worker.rs:382 is a latency stopwatch feeding `preflight::route`, not a decision input; doesn't need the injected clock. 'My mixed clock usage flag was wrong there.'" Verdict ADDRESSED (Andrea retracted).

**<Provider> infra anchor** — `src/batch/worker.rs:398` (`let resolved = match preflight::route(state, key, &model, Instant::now(), false).await` — the `Instant::now()` is the stopwatch start passed to `preflight::route`, which feeds `preflight::ms(start)` at `src/routes/preflight.rs:57-59` (`start.elapsed().as_millis()` — a pure *duration* computation, no wall-clock value used). The decision input at the same call site is `now` (line 377: `let now = clock.now();`), used for the key-revoked/expired check at line 378 — that IS the injected clock, correctly. So the same function uses both correctly: `clock.now()` for the wall-clock decision, `Instant::now()` for the latency stopwatch. (Note: the assignment cites line 382, which is `&row.batch_id` — the `Instant::now()` is at line 398; the gateway.md audit cites the worker.rs:382 region and the `Instant` import at worker.rs:13.)

**Codebase-intelligence backend** —
> `codegraph explore -p ~/<provider>/gateway "preflight route Instant now elapsed ms latency"` → confirms `preflight::route`'s `Instant` param feeds `ms()` (duration), not a wall-clock comparison.
> Serena `find_symbol` on `preflight::route` and `preflight::ms` (preflight.rs:57) to confirm the `Instant` is consumed only via `.elapsed()`.
> codebase-memory `trace_path mode=data_flow` from the `Instant::now()` call to confirm the value never reaches a `DateTime`/`expires_at`/lease comparison.

**Fix-suggestion policy** —
> SUGGEST ONLY: no fix — this paradigm is a *restraint* on the P-12-5 fix machine. If an automated agent applying P-12-5 flags `Instant::now()` at worker.rs:398, the correct action is to *not* open a finding and to record why (`Instant` = monotonic duration, `Clock` = wall-clock decision; `preflight::route` consumes it via `.elapsed()` only). The only "fix" is to ensure the doc-comment distinguishing `Instant` (stopwatch) from `Clock` (decision) is preserved if a future refactor moves the call.

**Adversarial caveat** — The paradigm is a *negative* one (don't flag X) and the only way it can be wrong is if a future refactor makes the `Instant::now()` value *also* feed a wall-clock decision — e.g. if `preflight::route` started comparing the `Instant` to a stored wall-clock. That refactor doesn't exist today (confirmed via the `ms()` consumer), so the restraint holds; the caveat is that the paradigm must be re-verified (re-trace the data flow) on every refactor of `preflight::route`'s signature, not assumed stable forever.

### P-12-7: Don't call a multi-file behavior change a "one-line fix"

**Paradigm statement** — When a reviewer's mental model of a fix is "one line" but the fix actually requires a new enum variant, match arms at every error-mapping site, and caller updates, the "one-line" framing is a smell in the *review* itself: it under-estimates the diff, under-allocates review time, and — if the author takes it literally — produces a fix that handles only one of N sites. The honest move when caught is to retract the size claim and itemize the sites, not to defend the original framing. A reviewer who inflates fix-size is annoying; a reviewer who *deflates* it (calls 15 lines "one line") is the one who leaves the other two match arms un-fixed.

**Source evidence** — `gateway.md` "Notes on the review — MAJOR-7 'one-line 403 fix' is ~15 lines across 3 files": "New variant + match arms + caller updates, not one line." Verdict ADDRESSED (Mateo's rebuttal verified true). Evidence: "`s3_client.rs:34` (variant) + `s3_client.rs:143,193,214` (three match arms) + `src/batch/sweep.rs:20-22` (sweep caller) + worker/route caller updates — well beyond one line."

**<Provider> infra anchor** — `src/batch/s3_client.rs:34` (`Forbidden(String)` enum variant — the new error type); `src/batch/s3_client.rs:143` (put-site 403 map), `:193` (get_range-site 403 map), `:214` (delete-site 403 map) — three match arms that had to learn the new variant; `src/batch/sweep.rs:20-22` (`Err(S3Error::Forbidden(e)) => { tracing::error!(...); Ok(()) }` — sweep caller that had to decide "skip not retry"); plus worker terminalize-on-Forbidden and route 403-return caller updates. A correct "fix 403 misclassification" touches *all* of these; calling it "one line" would have left, e.g., the sweep path still retrying 403 (the exact bug MAJOR-7 was about). **Fix-suggestion policy** —
> SUGGEST ONLY: this paradigm produces no code fix; it produces a *review-discipline* note. When a reviewer is about to write "one-line fix", the discipline is: first run `find_referencing_symbols` on the symbol the fix touches (a new enum variant, a changed function signature, a renamed column) and itemize the sites; *then* size the claim. If the itemization shows N>1 sites, the claim is "N sites across M files", not "one line". The PR author owns the actual fix; the reviewer owns the honest size estimate.

**Adversarial caveat** — The paradigm can be over-applied into "never call anything one line", which is pedantic — a truly one-line fix (e.g. `MAX_ATTEMPTS` → `MAX_DET_FAILURES` in P-12-1, a module-private rename with one call site) *is* one line and should be called that. The discipline is "verify the blast radius *before* sizing", not "always inflate size estimates". The strongest counter to this paradigm is a reviewer who, having been burned by an under-estimate, starts over-estimating every fix and generates noise on genuinely trivial ones — the resolution is the `find_referencing_symbols` check, which is O(1) and settles the question factually.

## Sector-specific failure modes

- **Flagging `Instant::now()` as a missing-clock smell (the P-12-6 false positive).** An agent applying P-12-5 broadly will sweep up every `Instant::now()` in the worker and call it "mixed clock usage". The fix is to trace the data flow: if the `Instant` is consumed only via `.elapsed()` (a duration), it's a stopwatch, not a clock decision. The agent must verify consumption (`preflight::ms`), not just call-site presence. Failure mode: an agent opens a finding to replace `Instant::now()` with `clock.now()`, which would *break* the latency stopwatch (wall-clock isn't monotonic) and introduce a real bug while "fixing" a non-issue.

- **Flagging every route-layer `Utc::now()` as a clock-injection smell (the P-12-5 over-application).** The route layer has many `Utc::now()` calls that are NOT smells: `usage.rs` lookback-default bounds (read-only query, no write), `admin.rs:825` key-expiry comparison (read-only), `models.rs:128` model-allow timestamp. The paradigm is scoped to **writes that stamp lifecycle/money timestamps** (create's `expires_at`, cancel's `cancelling_at`/`cancelled_at`), not "purge `Utc::now()` from routes". Failure mode: an agent generates a pile of false-positive findings on read-only defaults, burying the two real lifecycle-stamping smells.

- **Treating a silent NIT drop as "accepted by the author".** Three of Andrea's items (NIT-1, NIT-2, NIT-3) were silently dropped — no rationale in the reply, no `DECIDED-NOT-ACTIONED` verdict, just absent. An agent applying this sector must distinguish *addressed* (fix landed), *decided-not-actioned* (rationale recorded, like MINOR-4), and *silently dropped* (no rationale, like the three NITs). Failure mode: an agent reads "no response to this NIT item" and concludes "the author accepted the finding is invalid", when the truth is "the author didn't engage". The paradigm's fix-suggestion policy is to *re-open the finding with a recorded decision request*, not to close it.

- **Calling a module-private rename a "multi-site fix" (the P-12-7 over-application).** The `find_referencing_symbols` blast-radius check is meant to prevent under-estimating fixes that touch N call sites; applying it to a `const MAX_ATTEMPTS` with one in-file call site and calling it "a multi-site fix" is the opposite error. Failure mode: an agent runs the blast-radius query on every fix and inflates every one-line rename into a "cross-cutting change", generating noise. The discipline is to size *after* the query returns, not to assume the query will always return >1.
